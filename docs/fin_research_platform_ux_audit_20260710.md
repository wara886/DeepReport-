# 金融研报平台三市场与客户端体验审计

> 日期：2026-07-10
> 范围：A 股 `600519.SS / FY2025`、港股 `0700.HK / FY2025`、美股 `AAPL / 2025Q4`，以及数据源、手动导入、文档、证据、主张复核、评测和正式导出。
> 方法：真实 API 端到端运行、已有客户端截图复核、参考视频 15 分 14 秒关键帧复核。当前内置浏览器实例不可用，因此本轮没有新增真实点击截图。

## 1. 参考视频的答辩与展示方法

参考项目采用一条非常清楚的证明链，而不是逐个介绍菜单：

1. 首页先展示真实累计量、风险分布和处理漏斗，证明系统确实运行过。
2. 从采集任务下钻到清洗结果，展示任务配置、来源筛选、输入和处理状态。
3. 在清洗详情中把原文、OCR、实体、关系、风险标签和人工修改并排展示，证明结果可解释、可修正。
4. 展示人工复核前后状态变化，说明 Agent 不是黑盒自动发布。
5. 展示 PromptOps 的 system/user prompt、输入输出 Schema、版本选择和测试结果，证明系统可运营。
6. 展示实体库、关系图谱、风险线索和导出，形成“采集 → 处理 → 记忆 → 关系分析 → 复核 → 输出”闭环。

答辩时应沿一条真实案例走到底，每一步回答三个问题：输入是什么、Agent 做了什么、用户怎样核验或纠正。

## 3. P0：会直接破坏信任或阻断主流程

### P0-1 缺少官方证据时仍生成大量“财务事实”

A 股和港股任务的官方证据数均为 0，但系统分别沉淀 20 条财务事实和 14 条主张，来源全部是 `market_api`。产品必须明确区分：行情/第三方结构化数据、官方披露、规则推断、行业常识。没有官方披露时不能把前两者混成“已完成财务事实”。

建议：财务事实增加 `authority_level`、`fact_status` 和 `usable_for_formal_report`；正式研报只允许 primary/approved 事实进入核心财务章节。

### P0-2 单位和期间口径会被质量模型误判

AAPL 报告中的 `126.3B` 被质量复核解释成“126.3 亿美元，应为 1263 亿美元”。这暴露出英文 billion、中文亿、季度值、年度值和展示单位没有共同的机器可读合同。

建议：所有数值在进入 LLM 前统一携带 `raw_value/currency/scale/period_basis/source_period/display_value`，质量模型只比较结构化值，不从自然语言反推单位。

### P0-3 手动导入止于 stub，没有进入证据链

文本导入返回“解析成功”，但处理步骤 metadata 明确为 `stub: true`，文档详情中的证据数、主张数仍为 0。用户看不到“生成切片 → 提取证据 → 绑定公司/期间 → 用于任务”的下一步。

建议：导入完成后提供明确 CTA，并在文档详情展示转换漏斗与失败原因；`parsed` 不应表示已经可用于研究。

### P0-4 高质量分与“质量失败”并列

三个任务分数都在 0.89 左右，但全部不可交付。首页平均质量分显示为优秀，交付通过率为 0%，普通用户无法判断哪个指标才是真实结论。

建议：把评分拆成“内容评分”和“交付门禁”；只在门禁通过后显示“可交付”，未通过时首先展示阻塞原因而不是高分。

## 4. P1：显著降低效率和可理解性

### P1-1 运行进度不透明

任务耗时 68–85 秒，其中生成/LLM 节点占主要时间。客户端只显示“orchestrator/运行中”，没有节点中文名、当前动作、已耗时、预计剩余时间或取消/后台通知。

建议：直接消费 R0.3 的 `runtime_observability.node_latency_ms` 和 checkpoint，在任务行展示证据检查、检索、生成、质检、复核五步进度。

### P1-2 数据源初始为空，seed 后全部默认启用

新数据库的数据源页面为空；seed 后出现 14 个来源，但健康状态全为空且全部 enabled。启用、已配置、健康、最近成功是四个不同状态。

建议：首次启动自动 seed；缺 Key 的来源显示“未配置”，本地来源显示“可用”，远程来源经过健康检查后才能显示“健康”。

### P1-3 人工复核完成后仍显示“需要人工复核”

AAPL 15 条主张全部批准、LangGraph resume 完成后，剩余阻塞已经是证据和质量问题，但旧状态仍为 `review_required`。R0.3 已改为 `remediation_required`，前端显示“需要补证据或修复质量问题”。

### P1-4 失败后的修复动作不够闭环

系统能列出 `required_fixes`，但用户仍需自己在证据库、数据源、采集任务、主张复核之间判断去哪一步。缺少“一键创建补采集任务”“只重跑受影响章节”“修复后重新质检”。

### P1-5 客户端暴露内部英文键

评测中心会直接出现 `content_depth`、`llm_review` 等类别。用户需要的是“章节内容不足”“模型复核发现事实冲突”以及可点击动作。

## 5. P2：演示和日常使用的人性化缺口

1. 左侧大量入口标记“预览/增强中”，容易给评委或用户留下半成品印象；演示模式应只展示可完成闭环的入口。
2. 首页处理漏斗使用演示基准数字并附免责声明，真实数据与示意数据同时出现会削弱可信度。
3. 任务表操作按钮过多，建议收敛为主操作 + 更多菜单，并根据状态只展示当前可执行动作。
4. 评测页纵向过长，重要阻塞项被大量指标淹没；应先显示“为什么不能交付”和三步修复路径。
5. 实体库、关系图谱和投资线索在真实三市场运行中均为 0，没有把参考视频最有说服力的“记忆沉淀和关系发现”展示出来。
6. 成本始终为 0，但模型确实调用并产生时延；应明确是“未配置价格”还是“无成本”，不能直接显示 `$0`。
7. 导出中心应对 PDF/DOCX 显示文件校验、生成时间、版本和 SHA-256，而不只给下载链接。R0.3 已生成 manifest，前端还可继续增强展示。

## 6. 建议的演示主线

1. 选择一个已有官方材料的公司和期间，避免现场从空数据开始。
2. 首页展示真实任务数、官方来源覆盖和当前交付状态。
3. 打开采集批次，展示来源、文档、解析步骤和失败重试。
4. 从文档进入证据，再从证据进入 Claim，展示原文定位和引用绑定。
5. 展示 LangGraph 节点进度和一次人工复核 interrupt/resume。
6. 展示质量门禁：一个通过案例和一个被阻塞案例，并说明为什么系统拒绝交付。
7. 展示实体/关系/投资逻辑链，最后生成 PDF、DOCX 和可审计导出清单。

这条主线比逐页介绍菜单更接近参考视频，也更能证明平台不是“套壳聊天 + 报告下载”。
