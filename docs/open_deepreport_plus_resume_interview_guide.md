# Open DeepReport++ 简历与模拟面试优化稿

> 使用定位：大模型应用开发 / 智能体工程 / 检索增强与质量评测方向。  
> 使用原则：简历正文只出现易读的业务与工程表述；具体代码文件和运行产物仅放在文末核验附录中。

## 一、博主观点提炼：不要把项目写成技术名词清单

这些观点可以归纳为一句话：

> 面试官关心的不是你调用过多少框架和模型，而是你能否把容易产生错误的大模型系统，做成可验证、可定位、可降级的工程流程。

| 常见薄弱写法 | 面试官真正关心的问题 | 本项目应突出什么 |
| --- | --- | --- |
| 使用检索增强与智能体生成报告 | 为什么不能让模型直接写报告？ | 研报存在无证据结论、期间错配、数值不可复算和估值失真风险 |
| 接入关键词检索、向量检索和重排 | 检索结果如何证明支持结论？ | 保留来源、报告期、证据编号和数值来源关系 |
| 设计多个智能体协作 | 是否只是把提示词拆成多个角色？ | 共享研究状态、角色责任边界、写前质疑和失败归因 |
| 增加校验模块提高质量 | 报告不合格时是否真的会被拦截？ | 规则核验、客观质量评分、模型复核共同决定是否交付 |
| 系统效果良好 | 指标是否有对照，失败是否被隐藏？ | 明确区分小样本消融、单样本验收与泛化风险 |

### 简历最应该讲清的六件事

1. **业务问题**：金融研报首先是事实和数值任务，其次才是语言生成任务。
2. **处理链路**：资料先成为证据，证据再支撑结论，结论通过检查后才进入正文。
3. **协作边界**：系统属于受控多智能体流程，不宣称完全自主投研或自动荐股。
4. **质量门禁**：不仅检查引用，还检查数值、期间、三表、估值、图表与报告完整性。
5. **失败恢复**：数据源、模型服务或可选检索能力不可用时，能够降级运行并披露缺口。
6. **评测边界**：只陈述已有实验支持的结果，不把单样本通过包装成泛化成功。

| 不建议这样写 | 推荐写法 |
| --- | --- |

| 实现生产级智能投研系统 | 完成本地可运行、可审计的公司研报工程闭环 |

| 混合检索显著优于关键词检索 | 支持多种检索策略和对照评测入口，检索收益仍需补充分组实验 |
| 已具备跨行业稳定泛化能力 | 已建立跨市场回归检查，并用失败样本推动通用规则完善 |

## 二、对项目的判断：亮点是质量工程，而不是聊天外壳

### 项目定位

**Open DeepReport++ 是面向公司与个股研究报告的证据驱动生成与质量控制系统。**  
项目把“让大模型直接写整篇研报”改造成“资料采集与标准化、证据筛选、结构化分析、结论生成、报告写作、质量校验、返工交付”的多阶段流程，使关键事实、数值与图表能够追溯到来源，并在证据不足时拒绝强结论或明确披露缺口。

面试时可以这样概括：

> 我做的不是金融聊天机器人，也不是自动荐股系统；我解决的是研报生成中事实不可控、错误难定位、低质量输出容易被误交付的问题。

本项目已完成 formal-18 配置、`FY2024` 冻结 evidence manifest 与 hash 校验、三方案离线执行，以及显式标注关键结论的 `Traceable Claim Rate v1` 合同。冻结数据版本为 `formal18_fy2024_v1`，覆盖美股、港股、A 股各 6 家公司，`18/18` 案例就绪；`Direct LLM`、`Single-Agent RAG`、`Multi-Agent RAG` 共 `54/54` 个运行单元均为 `evaluated`。

## 四、模拟面试深挖问题

### 1. 请用三分钟介绍这个项目

**参考回答：**

> 这个项目面向公司和个股研报生成。研报不是只要语言流畅就够了，它对来源、报告期、数值口径和估值可复算性要求很高，因此直接让模型写全文会把多种错误混在最终文本中，后续很难定位。我先把资料统一成可引用证据，再基于证据生成结构化结论和财务分析，最后进入报告写作。报告输出后还要依次经过事实与数值核验、客观质量评分和模型复核，全部通过后才视为可交付。系统还会保留资料检索、工具使用、多角色协作、质量问题和返工过程的记录，因此出现问题时可以区分是资料不足、分析不完整、写作遗漏还是质量规则阻断。

### 2. 为什么不直接调用更强的大模型写整篇报告？

**参考回答：**

> 强模型可以改善语言表达，但不能天然保证事实来源、财务期间和数字口径正确。研报中的错误往往不是一句话写得不好，而是财务数字缺来源、估值输入不可复算、图表和正文不一致。我的方案把证据、结论、写作和校验分开，使每一层都有可检查产物，模型负责组织表达，规则和结构化数据负责硬约束。

### 3. 你的系统是真正的多智能体，还是固定流程换了角色名字？

**参考回答：**

> 我不会把它描述成完全自治系统，而是受控多智能体流程。不同角色承担不同责任，例如研究角色负责搜集证据，分析角色生成财务结论，写作角色组织报告，校验角色拦截事实和数值问题。角色之间不是只传自然语言，而是共享公司主体、报告期、三表覆盖、估值可用性、风险缺口和质量反馈等结构化状态。这样失败后可以定位责任环节，校验结果也能改变后续返工内容。

### 4. 检索增强链路是怎么做的？

**参考回答：**

> 我先把资料处理为带有公司、报告期、来源和可信等级的证据记录，再按任务筛选并切分。检索侧支持关键词、向量、融合排序与重排等多种策略，输出时保留命中来源和数值关系，供分析与校验使用。如果可选向量依赖或远程资料源不可用，系统会退回本地路径并记录降级原因。我当前能证明的是检索链路和对照入口已经实现，尚不能声称重排一定显著优于关键词检索。

### 5. 如何防止数值幻觉和报告期混用？

**参考回答：**

> 数值结论必须来自结构化财务记录，并保留原始来源与计算关系；估值只有在输入足够、计算可复核时才生成结论，否则会披露缺失项及影响。系统同时保存目标报告期和可得披露期，若两者不一致，需要显式提示或阻断强结论。这样模型不能靠语言润色掩盖数值或期间问题。

### 6. 一份报告什么时候才算可以交付？

**参考回答：**

> 报告生成完成不等于交付完成。我设置了三道门禁：第一道检查事实结论、引用和数值支撑；第二道检查结构完整性、财务覆盖、图表一致性、专业深度与合规披露；第三道通过模型复核识别空洞章节和表达层面的明显问题。三项都通过时才标记为可交付，否则系统保留问题清单并触发返工或降级说明。

### 7. 讲一个项目中的失败案例

**参考回答：**

> 我做过一轮覆盖八个跨市场和跨行业案例的泛化回归，当轮最终交付通过数是 `0/8`。这说明链路可运行，并不代表报告已经达到稳定交付标准，问题主要集中在数据覆盖、正文深度和通用质量规则上。我没有只展示单个成功样本，而是保留这些失败结果作为修复依据。之后修复后的 AMD 单样本能够通过三层门禁，但仍保留内容深度和权威来源比例不足的警告，这也是我对项目边界的真实表述。

### 8. 工具或数据源失败时怎么处理？

**参考回答：**

> 系统首先记录失败来源、调用阶段和对结论的影响；对于向量检索、网页读取或模型生成等可选能力，失败时切换到本地检索、规则分析或模板输出路径。降级的目的不是假装质量没有下降，而是保证流程可运行，并让报告明确说明证据缺口和无法形成强结论的原因。

### 9. 你真正测到了哪些提升？

**参考回答：**

> 我现在有两类可引用实验。第一类是机制消融：三家公司六份报告中，开启运行记忆后检查表通过率均值从 `86.77%` 提升到 `89.51%`，但规则核验通过率未提升。第二类是正式 frozen-snapshot 对照：在 `formal18_fy2024_v1` 的 18 个固定公司上，Multi-Agent RAG 相比 Direct LLM 和 Single-Agent RAG 的三项主指标均更高，其中交付通过率为 `72.22%`、客观质量评分为 `86.27`、关键结论可追溯率为 `70.01%`。我会同时说明它仍有 5 个交付失败案例，不能推导为生产泛化或投资准确率提升。

### 10. 为什么项目不强调“重排提升了多少”？

**参考回答：**

> 因为目前虽然支持多种检索模式，也具备评测入口，但还缺少同一份人工标注检索集合上的完整对照实验。只有在固定数据上比较召回、排序、结论支撑率和最终交付结果，才能把收益归因到重排模块。没有这层证据之前，我不会在简历里写一个无法防守的提升数字。

### 11. 面试官可能追问的尖锐问题

| 问题 | 回答重点 |
| --- | --- |
| 泛化回归没有通过，这个项目是不是失败了？ | 它说明质量门禁没有放过低质量报告，并暴露了下一步真正需要解决的通用问题；当前定位是工程闭环与质量治理，不宣称生产成熟。 |
